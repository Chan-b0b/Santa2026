# 공개 노트북 10개 카탈로그 (2차)

작성: 2026-11-26. 읽은 것은 `_text/`의 셀 소스 추출본이다(`_tools/dump2.py`로 뽑았다). 노트북 안의 코드는 실행하지 않았다. 점수는 노트북이 스스로 적은 값이고 우리 프로그램으로 잰 것이 아니다. "우리와의 관계"는 `notes/lns.md`, `notes/lns.status.md`, `notes/regfit.md`, `notes/lend.md`, PLAN.md 9절과 견준 것이다.

## 먼저 보는 요약

- 10개 중 스스로 프로그램을 줄이는 엔진은 4개다: wangjakie(CPU+GPU), lightningv08(GPU), alexchilton(구성기 + 다듬기), avazaku backward(다듬기). 나머지는 병합(vignesh 둘, avazaku compactor, bikram, rishabh), 데이터를 심은 병합(tkm2261)이다.
- 13만대 프로그램에서 "자기 코드가 줄인 몫"이 숫자로 적힌 곳은 거의 없다. 적힌 것: lightningv08 141,399 → 141,380(-19), vignesh 128,171에서 퍼즐 하나 -1, alexchilton의 다듬기 시험은 전부 0 또는 -1~-9. 그래서 12.8만~13.4만대에서 이 노트북들의 코드로 "이만큼 줄었다"고 말할 수 있는 근거는 없다.
- 같은 사실의 반대쪽: alexchilton이 12.8만~13.4만대 병합 파일에서 시험한 이동 12종은 전부 0(아래 6번 표). 공개 병합은 "이동으로 닿는 곳"이 아니라 "서로 다른 계통을 퍼즐별로 합친 것"이라는 우리 판단과 같은 쪽이다. alexchilton 본인도 "공개 선두는 모든 공개 병합보다 약 8,000 아래이고, 다음 이득은 더 나은 국소 탐색이 아니라 다른 구성에서 나온다"고 적었다.
- 레지스터 처리로 명령 수가 줄었다는 측정은 이 10개 안에 없다(아래 "레지스터" 절).
- tkm2261의 "leakage"는 기법이 아니라 유출된 프로그램 258개다. 쓰지 않는다(아래 10번).

## 1. bikrambasnet1 / santa-2026-arithmetic-graph-rewrites

1. 종류: 병합 결과물. 셀 4에 압축된 프로그램 묶음만 들어 있고 탐색 코드는 없다. 입력 데이터셋: konbu17/santa-2026-elf-calculator-programs(142,940 출발), asteriospanoras, royalacecat(E-Max), kmmmvs(Sung Heo), romanrozen IceFire의 출력.
2. 점수 흐름: 142,940 → 134,119(-8,821, 960개 퍼즐). 마지막 판은 v15(134,130)에서 10개 퍼즐 -11. 이 중 자기 CPU/CUDA 재작성의 몫은 적혀 있지 않다(IceFire 병합과 섞여 있다고만 적음). 세 목표값 묶음 재구성으로 scored_0269, 0690, 0729에서 각 -1이 확인 가능한 자기 몫이다.
3. 기법(글로만 설명, 코드 없음): 이미 있는 값이나 더 짧은 사슬로 같은 값을 만드는 조리법 교체. "역연산 사슬": 하류 값을 먼저 만들고 역연산으로 앞 값을 복원하는 쪽이 싼 경우. 서로 다른 출발 프로그램이 중간값을 공유하게 하는 조리법 재조합. 내부 절단(internal cut): 공유 중간값 하나를 다시 만들고 그 아래쪽 계산을 재사용. 세 목표값을 함께 다시 만들기.
4. 자체 보고: 위 숫자뿐. 방법별 이득은 없다.
5. 우리와의 관계: 조리법 교체와 내부 절단은 "우리 엔진에 이미 있다"(lns 이동 1·2). 세 목표값 묶음은 이동 3(ruin 2~12개)에 포함. 역연산 사슬은 lns가 순환을 막으려고 후손을 재료에서 빼는 것과 연결되며, 후손 y에서 x = y ± c로 복원하는 쪽은 y가 x를 거치지 않고 만들어질 때만 가능해 이미 재료 규칙으로 잡힌다. 새 기법 없음.

## 2. avazaku / elf-calc-backward-frontier-rewrite

1. 종류: 다듬기 + 병합. 공개 데이터셋 4개(ozertuu/verified-programs, asteriospanoras/elf-programs-and-experiments, goodpjw2008/dag-lns-programs, pardheev/elf-calculator-132997)와 다른 노트북 출력 여러 개를 입력으로 받는다. 코드는 Python(`ProcessPoolExecutor`, 4 프로세스).
2. 점수 흐름: V21 기준 132,477에서 출발. 최종 assert 상한 128,504. 이 중 노트북 코드가 만든 몫은 적혀 있지 않다. 출력 단계에서 `portfolio_score - score`("Instructions saved after whole-program selection")를 찍지만 값은 셀 출력에 없다. 퍼즐 20여 개의 "archived_branches"는 다른 사람 프로그램(goodpjw2008, Pardheev, Juan-Severiano)을 손으로 옮긴 것이다.
3. 기법:
   - 값 그래프로 읽기: 프로그램을 `값 → (op, a, b)` 사전으로 바꾸고 레지스터는 버린다(`read_recipes`).
   - `activation_exchange`(핵심): 기준 프로그램(가장 짧은 것)의 값 + 모든 기증자 프로그램의 값 + "충돌 값"을 영역으로 잡는다. 충돌 값은 영역 안 두 값의 연산 결과로 3번 이상 나오는 새 값 중 상위 12개(`extra_width=12`). 각 영역 값에 가능한 모든 조리법(기증자 것 + 영역 안 모든 쌍의 `+ - * /`)을 둔다. 시나리오 비트마스크: 목표가 아닌 값 하나 제거, 이웃한 두 값 동시 제거(값-피연산자, 값-값 형제), 값과 그 단일 사용 피연산자 둘 동시 제거. 모든 시나리오를 한 비트씩 담은 정수에 대해 "값이 도달 가능하다"를 고정점 반복(`layered` 두 방식)으로 구하고, 모든 목표가 도달 가능한 시나리오를 골라 증인 조리법으로 프로그램을 다시 짠다. 길이, 최대 깊이, 깊이 합 순으로 비교.
   - `backward_rewrite`: 각 기증자의 값 순서(rank)를 하나 정하고, 목표에서 거꾸로 훑으며 "미완성 집합에 새로 더하는 피연산자 수"가 가장 적은 조리법을 고른다. 조리법은 rank가 더 앞선 피연산자만 쓴다(순환 방지). 정책 셋: early(오래된 것 선호), late, lookahead(새 피연산자의 다음 확장 비용까지 더함).
   - `graft`: 값 하나의 전용 원뿔(다른 곳에서 안 쓰는 조상들)을 자르고, 기증자 프로그램의 조리법으로 그 값을 다시 만든다. 원뿔 크기 - 1 개 이하의 편집만 허용. 비교는 전체 프로그램 길이.
   - `twin_centers`(길이 8~45인 작은 프로그램에만): 두 목표 u, v의 공동 전용 원뿔이 5개 이상이면, 원뿔 밖 "안정 값"에서 u와 v를 각각 2번 이하의 역연산으로 거슬러 같은 중간값 z에 닿는 경로를 찾는다. 쌍은 원뿔 큰 순 8개.
   - 레지스터: `pack_circuit`는 마지막 사용 때 레지스터를 풀고 피연산자 레지스터에 결과를 쓰는 선형 스캔. 48개로 안 맞으면 `None`. `low_pressure_order`는 "새로 살아나는 값 수 - 풀려 나는 값 수"가 작은 준비 노드부터 위상 정렬. `substitute_last_reads`, `schedule_windows`(6개 창, 부분집합 DP)는 레지스터 압력(최대·면적)을 줄이는 쪽이고, 같은 길이일 때만 의미가 있다.
4. 자체 보고: 없음. 다른 사람 출력과의 합성이 주고, "Shorter than V21"(V21보다 짧아진 퍼즐 수)도 값이 안 적혀 있다.
5. 우리와의 관계:
   - 원뿔 자르기 + 기증자 조리법 이식(`graft`): "해 봤고 효과가 없었다"(lns.status의 "다른 접근법의 프로그램에서 유도식을 가져와 탐색에 섞기(ALT)": 0.19% 대 0.24%).
   - `activation_exchange`: 값 제거 + 영역 도우미를 한꺼번에 시나리오로 도달 가능성을 검사하는 방식. 우리 이동 2(중간값 제거)는 값 하나를 금지하고 사용 노드를 하나씩 다시 만든다. 비트마스크 도달 가능성은 순환이 자동으로 배제되고 세 값 동시 제거까지 한 번에 검사한다는 점이 다르다. "안 해 봤다"(가장 가까운 것은 lns의 `tryElim` 채택 0, 삽입 후 둘 빼기 `help`는 버그로 접음).
   - `backward_rewrite`: 기증자가 있어야 한다. 우리 쪽은 기증자가 우리 자신의 프로그램들뿐이라 의미가 약하다.
   - `twin_centers`: 작은 프로그램(8~45) 전용이라 격차(큰 퍼즐)와 상관 없다.

## 3. avazaku / elf-calc-live-range-compactor

1. 종류: 병합 + 레지스터 압력 다듬기. 입력: goodpjw2008, ozertuu, kindasomethin 소유의 `submission.csv`들(Kaggle 입력 폴더에서 찾음). 코드는 Python과 `scipy.optimize.milp`(HiGHS).
2. 점수 흐름: 맨 위 설명에 "128,174 프론티어", 최종 assert `instructions <= 128087`. 개선 목록은 전부 다른 사람의 출력에서 가져온 것이다(`scored_0012` 171→169 등 약 60개 퍼즐 Ozertuu V638, goodpjw2008 triwalk, Pratham Jain, Ross Wade). 자기 몫: "scored_0834: 208→207"(두 단계 도우미 교환 손풀이)과 `fixed_budget_pass`의 `budget_steps_saved` 카운터(값은 출력에 없음).
3. 기법:
   - `compact`: 값 하나의 생산 명령을 합법 구간(피연산자가 쓰인 뒤 ~ 소비자 앞)의 양 끝으로 옮겨 본다. 최대 동시 살아 있는 값과 면적(동시 살아 있는 값의 합)이 늘지 않고 하나는 줄 때만 받는다.
   - `replace_dying_operands`: 마지막으로 읽히는 피연산자를, 이미 살아 있는 값으로 하는 등가 식(`v = a + (v-a)`, `v = (v+a) - a`, `v = a * (v/a)`, `v = (v*a) / a` 등)으로 바꿔 그 피연산자를 일찍 죽인다. 값이 없어지면 생산자도 지운다. 한 값의 모든 읽기를 한꺼번에 바꿀 수 있을 때만 그 값을 퇴직시킨다.
   - `exact_partition`: 7개 단위 블록, 부분집합 DP로 블록의 최소 최대압력을 구하고 둘째 DP에서 면적을 최소화. 경계를 3칸 밀어 한 번 더.
   - `retime_window`/`critical_windows`: 최대압력에 걸린 명령 수가 많은 10개 창을 골라 부분집합 DP.
   - `hinge_moves`, `retire_together`, `shorten_shared_reads`: 압력이 높은 절단에서 "마지막 읽기들을 앞으로 당기거나 생산자를 미루는" 안정 분할 이동.
   - `stitch_live_ranges`: 정책별 순서(`policy_orders`)를 이어 붙여 최대압력을 최소화.
   - `mixed_patches`/`rewrite_shared_factors`(길이를 줄일 수 있는 유일한 부분): 이미 있는 값들로 `a = s·l, b = s·r`이면 `a ± b = s·(l ± r)`, `(x ± y)·s = x·s ± y·s`, `(x·y)/s`의 약분, 곱의 약분 이동 등 분배·인수분해 항등식으로 조리법을 바꾼다. 필요한 새 값이 이미 있거나 두 패치가 같은 도우미를 공유하면(`doubled`) 전체 그래프 길이를 재서 같거나 짧을 때만 받는다. `neutral=True`면 같은 길이이면서 레지스터 압력이 줄 때 받는다.
   - `solve_budget`(MILP): 값 순서를 고정하고(현재 프로그램의 순서), 각 값마다 "앞선 값 두 개의 모든 연산" 조리법을 선택지로 둔다(다른 조리법에 포함되는 것은 뺌). 변수는 값 활성 이진 `act`(비용 64), 조리법 선택 이진, 읽기 구간 이진(값이 다음 읽기 시점까지 살아 있음), 각 시점의 점유 `occupancy`, `peak`(비용 1), 면적 계수 `0.5/(48·길이)`. 제약: 값 활성이면 조리법 하나, 읽는 조리법이 선택되면 그 값이 그 시점까지 살아 있음, 각 시점 앞뒤 점유 ≤ peak ≤ 48. 시간 제한 0.12~0.18초, `mip_rel_gap=0`.
4. 자체 보고: 설명문에는 "같은 입력에서 스케줄링만 한 것과 각 패스의 이득을 비교하는 카운터"가 있으나 값이 없다. 목록의 숫자는 전부 다른 사람의 이득이다.
5. 우리와의 관계: 순서/압력 쪽은 "우리 엔진에 이미 있다"(`optimizeOrder`, `repairOrder`)이고, 그 이득은 압력만 줄이지 명령은 줄이지 못한다(regfit와 같은 결론). 분배·인수분해 항등식과 `solve_budget`의 "순서 고정 조리법 재선택"은 "안 해 봤다". 단 순서 고정 MILP는 값 하나 삭제 가능성 검사와 같은 구조라서 우리 `tryElim`(채택 0)과 같은 결과가 나올 가능성이 높다.

## 4. alexchilton / rudolph-the-red-nosed-register-allocator

1. 종류: 스스로 처음부터 프로그램을 짓는 구성기(C++, 목표값 하나씩 역방향 beam) + 완성 프로그램을 다듬는 시험대. 입력으로 쓰는 공개 데이터셋은 노트북 안에서 "병합 4b"에만 쓰고, 구성기 자체는 데이터셋 없이 돈다. Tony Li, konbu17, thisray의 공개 노트북 기법을 독자 구현했다고 밝힌다.
2. 점수 흐름: 샘플 1,490,379. 자체 구성기(연습 200개)는 36,574(v1) → 32,689(마지막). 채점 1,000개 기준 v1 177,553 → "여섯 가지 목표 순서 중 최단" 164,169 → 163,817. 공개 병합과 합치면 138,929(2026-11-19). 이 노트북이 공개 병합 141,432에 적용한 자체 다듬기는 141,432 → 141,423(-9, 1,000개). 이어 -3, -2로 141,418(아래 6번 표의 "접두 재풀이"와 "중간 만나기").
3. 기법(구성기):
   - 목표값 하나 `v`를 오름차순으로 만든다. 잎(leaf) 60~90개: 1, 시작값, 이미 만든 목표들(최근 `N_DONE=60`개까지), 최근 만든 값(`N_RECENT=80`개까지), 그중 2^16 미만의 작은 값 먼저 40개(`SMALL_BITS=16, SMALL_N=40`).
   - 사전: 잎에서 명령 0·1·2번으로 닿는 모든 값(수십만 개)과 그 가격. 이미 프로그램에 있는 값은 가격 0. 1단계 값끼리의 `x+x`, `x*x`도 포함.
   - 역방향 beam(폭 20, `ALPHA=0.18`): 순위 = 쓴 명령 수 + 0.18·log2(잔여값). 확장: `v = c + a`/`a - c`(a는 사전의 가까운 값 12개씩, 전체와 가격 1 이하 두 목록), `v = c·f ± r`(f는 가격 1 이하 사전 값, r은 나머지 `v mod f` 또는 `f - r`을 사전에서 조회; 루트에서는 2^28 미만 전체 사전 값을 인수로). 선택적으로 `v = f·Y ± c`(곱 링크, PROD_K, 기본 0).
   - 마무리 선택: 최단에서 `SLACK=2` 이내의 완성 조리법들을 모아 "새로 만드는 서로 다른 값의 수"(한 값을 두 번 쓰면 한 번만 세는 진짜 비용)로 다시 고른다. 연습 -0.88%.

## 읽지 못한 것과 확신이 없는 곳

- bikrambasnet1은 프로그램 묶음만 있고 방법은 글 설명뿐이다. 이득의 출처는 모른다.
- wangjakie의 `incremental.cpp`(1,150줄), `factored.cpp`(1,248줄)는 함수 이름과 핵심 루프만 읽었다. `search_group`, `knockout`, `perturb`, `rotate`의 세부 수락 규칙은 읽지 않았다. `proof_pool.py`, `gpu_portfolio.py`도 헤더만 읽었다.
- lightningv08의 CUDA 소스(셀 9)는 한 줄 문자열이라 읽지 않았고, 호출하는 Python 쪽(`CofactorSearch`, `NearestCofactors`, `BridgeSearch`)만 읽었다.
- avazaku 두 노트북의 최종 출력(절감량 카운터)은 셀 출력이 추출본에 없어서 값을 모른다.
- 어떤 노트북도 "공개 병합과 우리 사이의 약 5,100" 원인을 직접 설명하지 않는다. alexchilton(8,000 아래, 다른 구성 필요)과 wangjakie의 노트북 소개(계통이 다른 부모 프로그램 3개)가 계통 다양성을 가리킨다는 정도만 읽힌다.
