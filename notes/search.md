# search 접근법 노트 (1라운드)

구조를 가정하지 않고, "지금 쓸 수 있는 값(풀)"에서 목표까지의 짧은 유도를 탐색으로 찾는 방식이다.
코드는 `solvers/search/` 에 있다.

| 파일 | 내용 |
|---|---|
| `solver.py` | 본체. `Solver` 클래스, `solve_puzzle(pz, tbudget=…)`, `assign()`, `compact()` |
| `tiny.py` | `value_limit ≤ 64` 퍼즐의 최적해 (값 집합 비트마스크 BFS) |
| `seeds.py` | 숨은 씨앗값 찾기 (서로 다른 목표의 `t - c` 들이 공유하는 큰 약수) |
| `nt.py` | Miller-Rabin, 제한된 Pollard rho, 약수 나열 |
| `run.py` | 채점 퍼즐 전체 실행 (5 프로세스, 퍼즐별로 더 짧을 때만 교체) |
| `postpass.py` | 결과 파일의 프로그램마다 `compact()` 적용 |
| `bench.py` | 연습 퍼즐로 family 별 평균 길이 측정 |
| `show.py` | 프로그램을 값 수준으로 풀어 보기 (`show.py <csv> <id>`) |

실행 예:

```bash
python3 -I solvers/search/run.py --procs 5 --tlimit 120                     # 전체 1회 (7~9분, 기계가 바쁘면 13분)
python3 -I solvers/search/run.py --procs 5 --tlimit 120 seed=11             # 난수를 바꿔 한 번 더 (퍼즐별 최단만 남는다)
python3 -I solvers/search/run.py --procs 5 --maxbits 40 tbudget=3           # 작은 퍼즐만 재시작 반복
python3 -I solvers/search/run.py --procs 5 vcap=110 evict=big               # key=value 는 Solver 인자
```

## 2. 가장 중요한 발견: 탐색 풀을 레지스터 48개에 묶지 말 것

**레지스터가 필요한 것은 "앞으로 다시 쓰일 값"뿐이다.** 처음에는 풀 = 레지스터 48칸으로 두고 찰 때마다 하나를 축출했는데, 그렇게 만든 프로그램(45비트 이상 퍼즐)을 수명 분석해 보니 동시에 살아 있는 값이 시점 평균 25개, 퍼즐별 최대의 평균이 35개였다. 칸의 절반이 다시는 안 쓰일 값으로 차 있었다 (다른 접근법의 프로그램은 퍼즐별 최대의 평균이 41~43개).

지금 방식 (가상 풀, `virtual=1`):

- 탐색 풀에는 지금까지 만든 값을 160개까지 둔다 (`vcap`, 넘으면 LRU). 계획은 값 수준 `(op, x, y, v)` 로만 쌓는다.
- `L[k]` = k번째 명령 시점에 살아 있어야 하는 값의 수 (그 전에 태어나 k 이후에 쓰이는 값). 오래된 값 w 를 지금 쓰면 `(w 의 마지막 사용, 지금]` 구간의 `L` 이 1씩 늘어난다.
- 한도는 `CAP = 48 - 1 - 시작값 수` (시작값은 항상 살아 있다고 보고 따로 뺀다. 1은 결과를 쓸 자리).
- 계획을 실행하다 `L` 이 한도를 넘으면 그 계획을 통째로 되돌리고, 문제의 값을 풀에서 영구히 뺀 뒤 다시 계획한다 (퍼즐당 5~10번).
- 풀을 갱신할 때 "한도가 꽉 찬 시점을 건너야 하는 값"은 미리 뺀다. 그래서 자주 쓰이는 값이 저절로 남는다.
- 전에 만들었다가 풀에서 빠진 값이 다시 필요하면, 수명을 늘릴 여유가 있을 때 명령 없이 되살린다.
- 끝에 `assign()` 이 죽은 명령을 지우고 인스턴스별 수명으로 레지스터를 배정한다. `L ≤ CAP` 이면 항상 성공한다.

효과: 연습 200개 합계 34,549 → 32,051 (−7.2%, `vcap=110` 일 때), 채점 1회 실행 합계 약 169,600 → 157,596. 모든 family 에서 고르게 줄었다.
`vcap` 을 110 → 160 으로 올리거나 축출 정책을 바꿔도 1% 미만 차이다 (32,051 → 31,859). 수명 한도가 실제 제약이기 때문이다.

같은 생각의 작은 버전이 `compact()` 다. 축출됐다가 다시 만든 값을 한 번만 만들게 중복을 지우고 레지스터를 다시 배정한다. 기존 결과에 적용만 해도 279개가 줄었다.

## 3. 탐색 구조

### 3.1 비용 사전 C 와 표

- **F1**: 풀의 두 값으로 명령 1개에 만드는 값 전부 (`value -> (op, x, y)`). 풀이 바뀔 때마다 다시 만든다.
- **S**: 시작값만으로 트리 비용 k 이하에 만드는 값 표 (정적, 최대 60,000개, 보통 비용 5~6까지).
- **T2**: 풀에서 가장 작은 30개 값으로 명령 2개에 만드는 값 집합. 막혔을 때만 만든다. 조리법은 저장하지 않고 쓸 때 역방향 1단계로 다시 찾는다. 재료가 그대로면 캐시를 쓴다.
- **C**: `value -> 지금 추가로 드는 명령 수`. 풀 0, F1 1, T2 2, 나머지는 S 의 트리 비용. 모든 탐색이 이 사전 조회로 끝난다.

T2 를 넣은 것만으로 9% 줄었다. 큰 수 사슬의 꼬리(10~25비트 잔차)가 가장 비싼 부분이었기 때문이다.

### 3.2 정확 탐색 (목표에서 역방향)

- `cheap(t)`: 풀 값 p 하나를 피연산자로. `t = u op p` (u 는 C) 6가지 꼴, `t = q*p ± r` (q, r 은 C), `t = (p - e)/b ± d` (b, e, d 는 C).
- `deep(t)`: F1 값 w 를 피연산자로. `t = u op w` (u 는 C). 처음 90번 동안 한 번도 안 맞으면 그 퍼즐에서는 끈다 (임의값 퍼즐).
- 역방향 2단계: `t = u op p` 에서 u 를 다시 `cheap(u)` 로 푼다. 사슬 탐색의 앞쪽 노드 2개에서만 한다.
- 주 루프는 남은 목표 전부에 `cheap` → `deep` 을 돌려 가장 싼 목표를 먼저 만든다. 비용 3 이하가 없으면 3.3 으로 간다.

### 3.3 사슬 탐색 `chain_search(t)` (주력)

t 에서 거꾸로 내려가는 best-first 탐색이다. 노드는 "아직 만들어야 하는 값 하나", 우선순위는 `g + (0.8 + 0.15 × 비트수)`, 노드 100개까지.

| 간선 | 뜻 | 비용 |
|---|---|---|
| 풀 접합 | `v = q*x ± r`, x 는 풀, r 은 C → 자식 q | 2 + C[r] (r=0 이면 1) |
| F1 접합 | 위와 같되 x 는 F1 (2^10 이상), r 은 C≤2. 앞쪽 노드 6개만 | 3 + C[r] |
| 씨앗 접합 | x 는 아직 안 만든 씨앗값 (3.5절) | 할인된 씨앗 비용 + 2 + C[r] |
| 덧셈 근사 | `v = x ± r`, x 는 풀/F1 에서 v 에 가장 가까운 12개씩 → 자식 r | C[x] + 1 |
| 약수 | `v = d*e`, d 는 C≤3 → 자식 e | 1 + C[d] |
| 끝 | `cheap(v)` 가 성공 | 그 비용 |

추정이 싼 목표 2개에 대해 돌리고 더 짧은 쪽을 실행한다. `plan(t)` (q 와 r 을 둘 다 재귀로 푸는 AND 분해)도 함께 돌려 짧은 쪽을 고르고, 둘 다 실패하면 1에서 두 배/+1 로 만드는 `binary_steps` 가 유효성을 보장한다.

### 3.4 재계획

계획 길이가 12를 넘으면 앞의 3개 명령만 실행하고 다시 계획한다 (연속 6번까지). 새 작은 값이 풀에 들어가 나머지가 싸진다. 안 쓰인 명령은 끝에서 지워진다. 큰 시작값 퍼즐의 첫 목표가 40 → 27 정도로 줄었다.

### 3.5 씨앗값

`seeds.find_seeds`: 각 목표에 대해 `t - c` (c 는 0, ±시작값, ±시작값 둘로 만든 200 이하 값)를 만들고, 다른 목표들의 그런 값 전체의 곱과 gcd 를 구한다. 4096 미만 소인수를 떼고도 2^14 이상 남으면 숨은 중간값 후보다. 퍼즐당 0.03초.

- 연습 퍼즐에서 이런 공유 약수를 가진 목표 비율: shared 33%, multiplicative 27%, mixed 23%, independent 1% (우연 수준).
- `t2 = m*t1 + k` 같은 직접 관계에서 나오는 가짜 씨앗이 많다. 직접 관계로 묶이지 않는 목표가 2개 이상일 때만 쓴다.
- 씨앗을 보조 목표로 미리 만드는 방식은 2% 손해였다. 사슬 탐색의 곱수 후보로 넣고 비용을 "남은 사용처 수"로 나눠 매기면 평균은 중립, 씨앗이 뚜렷한 퍼즐(scored_0938 등)에서만 5% 정도 줄었다.

### 3.6 tiny 와 재시작

- `value_limit ≤ 64`: 값 집합을 비트마스크로 한 BFS. 레지스터 48개가 값 종류보다 많아 명령 하나가 새 값 하나와 같으므로 BFS 깊이가 최소 명령 수다. 16개 퍼즐 합계 57.
- `tbudget` 초가 남는 동안 설정과 난수(추정 상수, 동점 처리, 목표 선택)를 바꿔 다시 푼다. 0.1초짜리 작은 퍼즐은 수십 번 돈다.
- `seed=k` 로 전체를 한 번 더 돌리면 퍼즐별 최단 합계가 0.3~0.6% 씩 줄어든다 (첫 번째 154,462 까지 0.64%).

## 4. 알아낸 것

- **명령 하나의 정보량은 고를 수 있는 값의 수로 정해진다.** 풀이 48개면 곱수나 자릿수 하나에 5.6비트라서 접합 사슬은 2명령에 11~12비트, 58비트 임의 목표가 9.7개였다. 탐색 예산을 13배로 늘려도 1%도 안 줄었다. 줄이는 방법은 후보 풀을 키우는 것뿐이었다 (2절).
- **independent 는 정말 임의값이다.** 시작값 기준 6단계 표 23만 개로 `y*q + x` 분해를 찾아도 우연 수준이었고, 씨앗 비율도 1%다.
- **구조 있는 퍼즐의 목표는 "허브 ∘ 작은 상수 ∘ 작은 상수" 꼴이다.** 생성기는 시작값과 초기 작은 값을 피연산자로 써서 사슬을 만든다 (예: scored_0191 의 첫 목표는 시작값만으로 된 12단계 사슬). 그 사슬의 중간값이 다른 목표의 허브다. 내 탐색은 길이가 같은 다른 사슬을 찾아 버려서 허브를 놓치기도 한다.
- 하한(목표 개수)은 느슨하다. 작은 퍼즐도 최단이 하한의 2~3배다.

## 6. 약점

- chain 보다 합계가 1.5% 길다. 시작값이 작은 33~60비트 퍼즐(shared, mixed)에서 1.8%, 큰 시작값 퍼즐에서 1.1% 뒤지고, 32비트 이하는 같다.
- 기계가 바쁠 때(부하 30 이상)는 전체 1회가 15분 안에 안 끝난다. `timeout 870` 으로 끊고 중간 저장분만 남겼다.
- 수명 한도를 탐색 비용에 반영하지 않는다. 오래된 값을 쓰면 긴 구간의 자리를 차지하는데도 최근 값과 같은 비용으로 본다.
- 순수 파이썬이라 2단계 표 전체(약 100만 개)를 만들 수 없어 4~5명령짜리 정확 유도는 일부 꼴만 본다.

### 8.2 승자 프로그램 해독

`show.py best/best.csv <id>` 로 scored_0185 (lns 127), scored_0577 (lns 119), scored_0007 (quirk 136), scored_0156 (lns 118) 을 재생해 읽었다. 넷 다 같은 구조다 (0156 은 밑수가 2454, 3022, 4797 로 작다).

- **밑수 4~5개** (14~22비트). 예: 0577 은 18000, 66076, 80879, 17933. 0007 은 442937, 997340, 810679, 671048.
- **허브 = 밑수 쌍의 곱** (제곱 포함). 밑수가 4개면 허브 10개가 거의 다 나온다. 허브 하나를 목표 1~9개가 쓴다.
- **목표 = k·h ± r 또는 (h ± r1)·k ± r2.** k, r 은 생성기가 만든 작은 값 풀(시작값에서 몇 단계)에서 나온다. r 은 15~17비트까지 크다. 그래서 1라운드의 `(t - c)` gcd 씨앗(seeds.py, c 는 200 이하)이 대부분을 놓쳤다.
- 밑수도 그 작은 값들의 합·차다 (18000 = 17932 + 68, 28879 = 31009 - 2130). 작은 값이 밑수의 재료이자 다른 목표의 k, r 이다.
- 승자의 명령 배분 (0577, 119개): 작은 값과 밑수 35개, 허브 10개, 목표 31개에 74개 (목표당 2.4개).
- 내 프로그램 (0577, 177개)은 허브를 하나도 안 만들고 목표마다 사슬 5~6개를 썼다. 진짜 밑수와 허브를 손으로 넣어 주면 같은 솔버가 145, 작은 값까지 넣으면 135 가 나왔다. 부족한 것은 탐색이 아니라 **해독**이었다.

승자의 노트에서 가져온 것:

- quirk (`notes/quirk.status.md`): 목표가 `k·a·b + r` 꼴이라는 것, d 를 전부 훑어 `|t mod± d|` 가 작은 목표를 세는 방법.
- lns (`notes/lns.md`): 풀을 "최종 프로그램의 값 전부"로 보면 목표당 비용이 준다는 것. 작은 값을 먼저 풀에 넣어 두는 쪽으로 반영했다.

### 8.3 반영한 것

1. **보조 목표** (`Solver(aux=...)`). 허브, 밑수, 작은 값을 목표처럼 `remaining` 에 넣는다. 주 루프가 "가장 싼 것부터" 만들기 때문에 작은 값 → 밑수 → 허브 → 목표 순서가 저절로 된다. 안 쓰인 보조 값은 `assign()` 이 지우고, 계획이 9개를 넘는 보조 값은 포기한다.
2. **허브·밑수 해독** (`hubs.py`, `decode3.py`, C++ `basescan.cpp`, `partnerscan.cpp`). 방식이 넷이고 퍼즐마다 맞는 것이 다르다.
   - `simple`/`pin`: 목표 쌍의 연분수에서 `|q·t2 - p·t1|` 이 작은 근사분수로 허브 후보를 만들고, 후보끼리의 gcd 로 밑수를 뽑는다.
   - `d3`: basescan 이 d 를 2^11~2^23 까지 훑어 `|t mod± d| ≤ 64` 인 목표가 포아송 기대보다 많은 d 를 씨앗으로 잡고, partnerscan 이 씨앗 a 마다 x 를 2^22 까지 훑어 `a·x` 의 지지 목표를 센다. 허브 수준에서는 17비트 나머지도 작아서 basescan 이 놓친 짝이 잡힌다. 퍼즐당 0.3초 + 씨앗당 0.4초.
   - `tri`: 근사 허브 셋이 `H1 ≈ a·b, H2 ≈ a·c, H3 ≈ b·c` 이면 `a = sqrt(H1·H2/H3)` 가 정수로 정확히 나온다 (제곱 허브는 `a = round(sqrt(H))`). 세 곱이 모두 근사 허브와 W 안에서 맞는 것만 받는다. 나머지가 커서 basescan 이 0개를 찾는 퍼즐(0007)에서 밑수 4개를 정확히 복원했다. 순수 파이썬으로 퍼즐당 0.05초. W 를 2^9~2^17 다섯 가지로 돌려 설명하는 목표가 가장 많은 것을 쓴다.
   - `uni`: 위 셋의 밑수 후보를 모아, 쌍의 곱이 새 목표를 2개 이상 설명하는 것만 탐욕으로 고른다 (`greedy_bases`). 배수 제거, 인수 옮기기, 가지치기로 정리한다.
3. **작은 값 해독** (`decode_smalls2`). 허브가 정확하면 목표마다 k, r (또는 r1, r2) 이 정해진다. 나머지를 `k·r1 + r2` 로 쪼갤 때 다른 목표가 이미 쓰는 값이 나오는 쪽을 고른다. 이 값들을 보조 목표로 넣으면 밑수가 명령 2개로 만들어지고(전에는 4~6개) 목표당 비용이 3.8 → 2.3 으로 내려갔다 (scored_0185: 보조 61개 + 목표 75개 = 136).
4. **PyPy 로 실행.** 같은 코드가 3~4배 빨라서 퍼즐마다 해독 변형 2~3개를 풀어 최단을 고를 수 있었다.

실행: `.tools/bin/pypy3 -I -u solvers/search/run.py --hubs --procs 5 --tlimit 90 modes=tri` (modes 는 `simple+pin`, `tri`, `tri2`, `uni`, `uni2`, `d3` 가운데 고른다. `d3` 와 `uni` 는 `basescan_all.txt` 와 `decode3.json` 이 먼저 있어야 한다).

### 8.5 다음 아이디어

1. 두 겹 목표 해독: `K = round(t/h)` 의 약수 k2 (이미 아는 작은 값) 마다 `c = t mod± k2`, `u = (t - c)/k2` 를 만들고 u 를 한 겹 목표로 해독한다. u 를 보조 목표로 넣으면 그런 목표가 5~6개에서 4개쯤으로 준다.
2. 해독을 "가장 싼 것부터"에 맡기지 말고 전용 구성기로: 작은 값 집합 N (k, r, r1, r2 전부) 과 밑수를 한꺼번에 놓고, N 안의 값 둘로 만들어지는 값부터 잇는 최소 신장 트리식 구성. 지금은 보조 목표 변형 3개(전부, 4096 미만 또는 2회 이상, 2회 이상) 중 최단을 고르는데 퍼즐마다 ±10 흔들린다.
3. `ps` (작은 밑수 쌍 훑기)를 전체 퍼즐에, AMIN 을 2^8 로 낮춰서. 지금은 퍼즐당 2.6초(기계가 바쁘면 8초)라 496개 중 483개만 돌렸다. `a*b` 를 직접 도는 대신 h 를 2^20~2^27 로 한 번 훑고 약수를 나누면 더 빠르다.
4. 0577 유형: basescan 의 d 목록 전체(배수·약수 포함)를 후보로 두고, 후보 넷을 골라 쌍의 곱 10개가 설명하는 목표 수를 최대화하는 조합 탐색 (C++).
5. 밑수 셋의 곱, `k·a·b` 에서 k 가 큰 허브(8966·80879)를 허브 후보에 넣기.
6. 완성된 프로그램을 lns 처럼 다시 유도하는 일은 lns 가 이미 내 결과를 입력으로 하고 있으니 여기서는 하지 않는다. 대신 해독 결과(`decode3.json`, `tri` 의 밑수)를 quirk 와 맞춰 보면 서로 놓친 퍼즐을 채울 수 있다.
