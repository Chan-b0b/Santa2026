## 2. 핵심 아이디어

목표값 하나를 "지금 레지스터에 있는 값(풀)에서 명령 몇 개로 유도되는가"로 보고, 남은 목표값 중 `비용 - 0.16*비트수` 가 가장 작은 것부터 만든다.
유도의 중간값은 전부 풀에 남아 다음 목표값의 재료가 된다. factor 고유의 부분은 **소인수분해로 곱 분해 후보를 직접 나열하는 것**이다:
60비트 수의 Pollard rho(Brent) 분해가 순수 Python 으로 평균 0.2ms 라서(`nt.py`), `t`, `t ± c` 를 수천 번 분해해도 된다.

### 2.1 풀과 비용표 (`engine3.py`)

- **풀**: 지금까지 만든 값 중 "아직 레지스터에 둘 수 있는" 값 전부(실제로 60~120개). 레지스터는 다시 쓰일 값에만 필요하므로 48개보다 많이 둘 수 있다.
  - `live[j]` = 명령 j-1 과 j 사이에 살아 있어야 하는 값 수. 값 u 를 다시 쓰면 `lastuse[u]+1 .. 지금` 구간이 1씩 는다.
  - 어느 구간이 `cap`(46)에 닿으면 그 구간 이전에 마지막으로 쓰인 값은 다시 쓸 수 없으므로 풀에서 뺀다(`_reap`). 시작값은 항상 살아 있는 것으로 센다.
  - 끝에서 `emit()` 이 마지막 사용 시점 기준으로 레지스터를 배정한다. 48개를 넘으면 `run.py` 가 cap 36, 30 으로 다시 푼다(지금까지 실패 0건).
- **F1**: 풀 값 둘의 `+ - * /` 한 번으로 나오는 값의 사전 `값 -> (op, a, b)`. 풀에 값이 들어올 때 증분 갱신(값 하나에 0.2ms). 풀 100개면 1.1만~1.6만 개.
- **L2/L3/L4** (명령 2~4개짜리 값의 집합, 원소만 저장하고 유도는 쓸 때 다시 찾는다):
  - 풀 28개 이하(mode 0): L2 = F1 op 풀 전체. 풀 10개 이하이면 L3, 5개 이하이면 L4 도 만든다(각 70만~120만 개 이하일 때만).
  - 풀 29개 이상(mode 1): 2^20 이하의 값만 L2 로 둔다(작은 F1 값 op 작은 풀 값, 증분 갱신). 큰 값의 2 명령 여부는 그때그때 `two_loop` 으로 확인.
  - `cost(w)`: 풀 0, F1 1, L2 2, L3 3, L4 4, 없으면 ∞. 전부 집합 조회라 O(1).

### 2.2 유도 종류 (싼 것부터 시도)

| 이름 | 꼴 | 명령 수 | 찾는 법 |
|---|---|---|---|
| one | t ∈ F1 | 1 | 사전 조회 |
| two | t = x op c (x ∈ F1, c ∈ 풀) | 2 | 풀을 훑으며 `t-c, t+c, c-t, t/c, t*c, c/t ∈ F1` |
| chain3 | t = (x op c) op c' | 3 | mode 0: `back1(t)` ∩ L2. mode 1: 집합 연산으로 일괄 (`{w-z for w in W} & F1.keys()` 를 풀 값 z 마다) |
| pair | t = x op y (x, y ∈ F1) | 3 | `{t-x for x in 새 F1 키} & F1.keys()` 등. 새로 생긴 F1 키에 대해서만 증분 검사 |
| pair12 | t = x ± z (x ∈ F1, z ∈ L2) | 4 | `{t-x for x in F1} & L2` |
| mitm (mode 0) | 풀 값으로 뒤로 k 단계 간 값이 표에 있거나, t = (L_i 값) ± (L_j 값) | k+j | 뒤로 가는 값 집합이 6만 개 이하인 동안 확장 |
| **fsplit** | t = d·e, 약수를 재귀로 다시 쪼갬 | 1 + 비용(d) + 비용(e) | t 의 약수 전체에 `dcost(d) = min(cost(d), min dcost(a)+dcost(b)+1)` 메모이제이션 |
| **shift** | t = d·e ± c, c − d·e (c ∈ 풀) | 2 + 비용(d) + 비용(e) | 풀 값 c 마다 `t∓c` 를 소인수분해해 약수쌍 조회. 2^46 이하일 때만 |
| decomp | t = q·x ± r, q 가 표에 없으면 한 단계 더 | 2 + 비용(x) + 비용(r) + 비용(q) | x 는 풀/F1 전체. `[x for x in F1 if (v % x) in pool0 or ... in F1 or ... in L2]` 한 줄로 거른 뒤 계산 |
| fallback | decomp 를 깊이 4→9→18 로 | | 가장 작은 목표 4개 중 싼 것. 그래도 안 되면 1, 2, 3 … 을 풀에 심는다 |

- **shift 의 일괄 검사**가 multiplicative/shared 에서 가장 많이 듣는 factor 고유 장치다. `t∓c = a·b` 에서 a 가 풀 값(비용 0)이고 b 가 표에 없을 때,
  그런 b 를 전부 모아 `{b-z for b in B} & F1.keys()` 를 풀 값 z 마다 한 번씩 돌린다. 맞으면 `t = a·((x op y) ± z) ± c` 로 명령 4개다.
  약수쌍을 소인수분해로 나열하지 않으면 a 후보를 일일이 나눠 봐야 해서 풀 100개에서는 쓸 수 없다.
- **fsplit** 은 약수가 400개를 넘으면 건너뛴다. 제곱(`d = a·a`)은 a 를 한 번만 만든다.
- 합친 유도는 값 기준으로 중복을 지운 뒤의 길이를 비용으로 쓴다(같은 중간값을 두 번 세지 않음).

### 2.3 목표값 순서: 게으른 갱신

- 매 회: (1) F1 에 있는 목표는 전부 만든다. (2) two 가 되는 목표 하나. (3) chain3(mode 0)/pair 가 되는 목표 하나. (4) 그 밖에는 `deep(t)` 캐시에서 `비용 - 0.16*비트수` 최소인 목표.
- `deep(t)` 는 풀이 100개일 때 5~25ms 라서 매 회 전부 다시 잴 수 없다. 목표마다 (비용, 유도, 풀 버전)을 캐시하고, 매 회 가장 오래된 `refresh` 개만 다시 잰다.
  고른 목표의 캐시가 오래됐으면 그 자리에서 다시 재고 최솟값을 다시 고른다(오래된 유도는 절대 적용하지 않는다).
- **`refresh` 가 클수록 좋다** (연습 22개 부분집합: 2개/회 3,528 → 전부 3,442, -2.4%, 시간 2.6배). 기계가 한가하면 12개/회, 바쁘면 6개/회가 15분 안에 들어온다.
  남은 목표값 비율보다 시간이 많이 지났으면 재평가 수를 1/3 또는 1개로 줄여 마감을 넘기지 않게 한다(시간 배분).
  chain, relate 노트의 "매번 전부 다시 재는 것이 값을 한다"와 같은 결과다.

### 2.4 씨앗 채굴 (`seeds.py`): 소인수분해로 숨은 기준값의 인수 찾기

- shared/multiplicative 목표값은 `t = k·h + e` (h: 숨은 기준값, k, e: 싼 작은 수)가 많고 기준값끼리 인수를 공유한다 (practice_0004: 919, 223).
- 싼 보정값 e (0, ±시작값, ±시작값 둘의 연산 한 번, 4096 이하, 최대 97개)마다 `t - e` 를 소인수분해해 2^7 이상 `t/2` 이하의 약수를 모으고, 약수 d 를 가진 목표값 수로 투표한다.
- 작은 d 는 우연히도 많이 걸린다. 우연 기대치 `exp = 목표 수 × min(1, 보정값 수 / d)` 를 빼서 점수 `(투표 - 1 - exp) × 비트수(d)` 를 매기고,
  투표가 `exp < 0.05 → 2`, `exp < 0.4 → 3`, 그 밖에는 `4·exp + 2` 이상인 것만 남긴다. 같은 목표 묶음을 설명하는 약수는 점수 높은 것 하나만 쓴다.
- practice_0004 의 상위 후보: 29510928 = 2^4·3^2·223·919 (4표), 29408 = 2^5·919 (6표), 3676 = 4·919 (7표), 2676 = 12·223 (6표).
- 쓰는 법은 what-if 다: 후보 하나를 먼저 만들어 풀에 넣고 전체를 다시 풀어, 짧아진 퍼즐만 채택한다 (`--cfg '{"seedk":[0]}'`).

## 3. 유형별로 통한 것과 안 통한 것

연습 퍼즐에서 목표값 크기별 유도 비용(명령 수)의 최빈값. 괄호는 그때의 풀 크기 중앙값 (v3 기준).

| 비트 | multiplicative | shared | mixed | independent |
|---|---|---|---|---|
| 16–23 | 3~4 (38) | 3~4 (18) | 4 (21) | 4~5 (24) |
| 24–31 | 4 (79) | 4~5 (44) | 5~6 (28) | 6 (39) |
| 32–39 | 5 (106) | 5 (68) | 6 (54) | 6 (61) |
| 40–47 | 6 (122) | 6 (103) | 6~7 (92) | 6 (97) |
| 48–55 | – | 6~7 (115) | 7~8 (107) | 7~8 (105) |
| 56–63 | – | 7~9 (122) | 9 (111) | 9~10 (108) |

**통한 것**
- **풀을 레지스터 수가 아니라 수명으로 제한하기.** 풀을 46개로 묶고 L2 전체를 유지한 v2 는 연습 합계 39,884, 수명 기반 큰 풀(v3)은 34,003. 큰 풀이 모든 유형에서 이긴다(F1 크기가 풀의 제곱).
- **shift (t = d·e ± c)**: multiplicative 40개 퍼즐에서 유도의 약 절반(v1 기준 목표값 1,161개 중 546개, fsplit 219개). shared 에서는 "기준값 근처 값 × 작은 수 ± 작은 수"를 명령 4개로 잡는다.
  채점 1,000개에서 R1 기준 shift 4,106회 20,636개 명령, fsplit 997회 5,108개 명령.
- **decomp (t = q·x ± r)**: 40비트 이상 목표값의 주력(채점 1,000개에서 14,568회, 전체 명령의 66%). x 를 풀이 아니라 F1 전체에서 고르는 것이 중요하다.
- **풀이 작을 때의 표(L3/L4)와 mitm**: 초반 목표값과 목표값 10개 안팎의 작은 퍼즐에서 명령 3~4개짜리를 찾는다.
- **`비용 - 0.16*비트수` 선택** (chain 노트에서 가져옴): 연습 22개 부분집합에서 shared 634 → 616, multiplicative 776 → 772.
- **이진법 대신 깊은 decomp + 작은 정수 심기**: 시작값이 1~3개이고 목표값이 60비트인 퍼즐에서 첫 목표값이 70~90개 → 16~20개. independent 평균은 v1 294 → v3 245 (다른 변경 포함).
- **빠른 퍼즐의 무작위 재시작**(퍼즐당 예산 3.5초): multiplicative 4,494 → 4,444. 다른 유형은 재시작할 시간이 없어 그대로다.

**안 통한 것 (전부 꺼 두었거나 지웠다)**
- **목표값끼리의 직접적인 곱셈 관계는 드물다.** 100 넘는 소인수를 다른 목표값과 공유하는 목표값은 multiplicative 9%, shared 12%, mixed 7%, independent 4%(우연 수준).
  `gcd > 1000` 인 짝이 있는 목표값은 multiplicative 14%, shared 18%. 즉 "공통 인수를 한 번 만들고 곱셈 사슬로 조립"만으로는 목표값의 80% 이상을 못 덮는다.
- **hub**: 풀 값 하나와의 연산 한 번으로 목표값 2개 이상에 닿는 공통 중간값을 찾아 먼저 만들기. 연습 200개에서 8번(33개 명령)만 걸렸다.
- **t ± c 분해를 46비트 넘는 수에 쓰기**: 두 약수가 모두 싼 경우가 사실상 없고(practice_0100 에서 0회) 분해가 그 퍼즐 시간의 약 20%를 썼다.
- **중간 크기 L2 (F1 op 작은 풀 값, 2^36 까지)**: 어림으로는 34비트 이하 목표값이 `F1 ± F1 ± c` 로 명령 4개에 되어야 하는데 실제로는 이득이 없었다(22개 부분집합 3,567 → 3,573). practice_0100 에서 시간의 9%를 썼다.
- **decomp 에서 q 를 F1 op F1 로 끝내기**(q 가 표에 없을 때 3개 명령짜리인지 검사): 변화 없음.
- **beam 폭/깊이 늘리기** (4 → 16 → 64, 깊이 2 → 3): 1% 이내. 탐색 폭이 아니라 풀의 정보량이 한계다.
- **끝에서 다시 유도하기**: 완성된 프로그램에서 한 목표값만 쓰는 단계를 지우고 최종 풀로 다시 유도해도 줄지 않는다.
  practice_0100 (60비트 31개, 304개 명령)에서 목표값 전용 단계는 186개, 나머지 118개(39%)는 여러 목표값이 같이 쓰는 값이다.
- **씨앗을 무조건 먼저 만들기**: 1순위 씨앗을 넣은 실행 단독으로는 기준과 같다(shared 7,471 → 7,493). 퍼즐별 최단을 고를 때만 이득이다.

**유형별 진단**
- multiplicative: 목표값이 작아서(대부분 2^31 이하) 풀이 40개를 넘으면 명령 3~4개에 걸린다. 비용의 대부분은 풀이 작은 초반 10개 목표값이다.
- shared: 군집의 첫 값이 5~7개, 나머지는 2~4개. 기준값이 목표값이 아니면 일반 유도가 우연히 지나가야 풀에 들어온다.
- mixed: 작은 절반은 shared 처럼, 큰 절반(48~60비트)은 independent 처럼 든다.
- independent: 균일 난수로 보인다. 60비트는 2단 decomp 로 9개 안팎이고, 풀 100개에서 폭을 늘려도 내려가지 않는다.

## 4. 한계

- 60비트 난수 목표값은 `(x ∈ F1) × (q) ± (r ∈ F1 또는 L2)` 를 두 번 겹쳐야 해서 단마다 4~5개가 든다. 한 단에 30비트를 줄이려면 30비트짜리 r 이 표에 있어야 하는데 순수 Python 으로는 그 크기의 2 명령 표(수백만~천만 개)를 유지할 수 없다.
- `deep` 한 번이 5~25ms 라 매 회 전체 재평가를 못 한다(2.3절). chain 보다 1.5% 긴 차이(153,803 대 151,459)의 큰 부분이 여기서 나오는 것으로 본다(확인하지는 못했다).
- 초반 3~5개 목표값(풀이 30개가 되기 전)에 퍼즐당 15~25개가 더 든다.
- 씨앗 what-if 는 후보마다 전체를 다시 풀어야 해서 15분 실행 한 번에 후보 하나만 본다.

## 5. 다음에 해 볼 것

1. **`deep` 을 싸게 만들어 매 회 전부 다시 재기.** 새로 들어온 풀/F1 값만 x 후보로 쓰는 증분 decomp 를 모든 목표에 돌리고, 전체 재평가는 고른 목표에만 한다.
2. **씨앗 후보 여러 개를 한 번에.** 지금은 후보 하나씩이다. 같은 소인수(예: 919)를 가진 후보 묶음을 같이 넣거나, 씨앗을 만든 직후 그 씨앗으로 나누어지는 `t - e` 를 가진 목표값을 먼저 만드는 순서를 강제한다.
3. **`t - e` 의 e 를 F1 전체로.** 지금은 시작값에서 한 번 연산한 값까지만 본다. 풀이 자란 뒤(작은 값이 30개쯤) 다시 채굴하면 e 후보가 늘어난다.
4. **chain 의 근처값 이동과 결합.** decomp 의 q 가 풀/F1 값 근처일 때 차이를 다음 상태로 넘기는 이동이 없다(shared 에서 chain 이 더 짧은 이유로 보인다).
5. **작은 퍼즐 정확해.** `value_limit` 40 이하의 BFS 는 relate/chain/search 가 이미 갖고 있다. factor 는 127개 작은 퍼즐에서 합계 190개쯤 길다.

## 6. 다른 접근법이 가져갈 수 있는 것

- `nt.py` 의 `factor()`: 60비트 수 평균 0.2ms. 채점/연습 목표값의 분해는 `cache/factors_*.json` 에 있다(`precompute.py`).
- **약수쌍 + 집합 일괄 검사** (2.2절 shift): `t∓c = a·b` 의 b 후보를 모아 풀 값 z 마다 `{b-z for b in B} & F1.keys()`. 명령 4개짜리 `a·((x op y) ± z) ± c` 를 찾는다.
- **한 줄 필터로 decomp 후보 거르기**: `[x for x in F1 if x < v and ((r := v % x) in pool0 or r in F1 or r in L2)]`. F1 1.6만 개에 1.5ms.
- **씨앗 채굴의 우연 기대치 보정** (2.4절): gcd 만 쓰는 것보다 후보가 많고, 작은 약수의 거짓 양성을 걸러 준다.
- 풀이 작을 때만 L3/L4 표를 만드는 단계적 표 (2.1절).

  엔진은 목표를 하나씩 탐욕으로 만들며 그때마다 필요한 작은 수(k, r)를 새로 만든다. best 프로그램은 `4·허브` 같은 허브 배수와 작은 수를 3~8번씩 나눠 쓰고, 목표를 맨 허브가 아니라 **이미 만든 다른 목표나 중간값 기준**으로 설명한다 (scored_0011: `T2 = T1 + 48`, `T = (4h + 48)·36`).

- **해독 안 된 구조형 퍼즐.** 16:37 집계(해독 v3 기준, 목표 20개 이상인 퍼즐)에서 best 가 목표당 4.3개 미만인데 해독이 안 된 퍼즐이 중앙값 24비트 이상에 111개(차이 합 2,048) 있었고, 중앙값 24비트 미만인 미해독 퍼즐은 105개(993)였다.

- **난수형 (중앙값 48비트 이상).** 이번에 손대지 않았다 (PyPy 로 한 번 더 풀어도 scored_0001 이 252 로, 여러 번 돌려 모은 기존 246 보다 길었다). chain, search 가 이 단계에서 각각 146,769, 147,330 으로 내려가 factor(150,195)보다 짧아졌고, best 는 미해독 48비트 이상 209개에서 factor 보다 4.5% 짧다.

### 8.6 다음 아이디어

1. **해독 결과를 직접 쓰는 전용 구성기.** `anchors.explain()` 이 목표마다 (k, r, a, b)를 준다. 지금은 씨앗만 넣고 엔진에 맡기는데, 필요한 작은 수 집합 {k} ∪ {|r|} 을 미리 알고 있으므로 "닻의 배수로 그 집합을 가장 싸게 덮는 작은 수 풀"을 먼저 설계하고, 같은 허브의 목표를 묶어 `k·허브` 를 공유하게 순서를 정한다. 목표: 밑수 뒤 목표당 3.75 → 3.0.
2. **겹친 꼴 해독.** `t = (k1·h + r1)·k2 + r2` (scored_0136 의 `256·(12a² + 4133)`) 는 지금 r 이 커서 "설명 안 됨"으로 남는다. t 를 닻의 작은 배수로 나눈 몫에 같은 검증을 한 번 더 돌리면 잡힌다.
3. **밑수의 2~4배 변형을 쌍 검증에 넣기.** scored_0432 처럼 허브마다 배수가 다른 퍼즐은 후보 a 에 대해 a/2, 2a, 4a 를 같은 정수로 보고 지지 목표를 합친다. 작은 밑수(10~14비트) 퍼즐 100개쯤이 대상이다.
4. **밑수 구성 비용.** 엔진은 20비트 밑수 하나에 5~6개를 쓴다. scored_0011 의 best 프로그램은 닻과 그 배수(601, 2404, 38480 …)를 밑수 구성에도 써서 밑수 3개에 작은 수 포함 25개 안팎을 쓰고 그 작은 수를 뒤에서 다시 쓴다. 닻을 먼저 만든 뒤 밑수를 `닻배수 × 닻배수 ± 작은 수` 꼴로 찾는 전용 탐색을 넣는다.
5. **해독 파일 공유.** `solvers/factor/cache/dec2_scored.json` (`{id: {"bases": [...], "cov": 설명된 목표 수, "n": 목표 수}}`) 은 씨앗 인터페이스가 있는 relate, chain, search 가 그대로 읽어 쓸 수 있다. v3 시점(16:45)에 해독된 239개 가운데 `results/quirk.csv` 에 결과가 없던 퍼즐이 58개였다.
6. multiplicative 유형은 숨은 정수 해독이 아니라 지금의 fsplit/shift 와 lns 식 재합성이 맞는 도구다. factor 안에 재합성을 다시 만들기보다 lns 의 출발점을 좋게 하는 쪽이 싸다.

### 8.7 이번에 더한 파일과 실행법
