# regfit: 레지스터 48개 때문에 버려지는 개선 이동의 측정

작성: 2026-11-25. 코드는 `solvers/regfit/`. 결론: 버려지는 개선 이동이 거의 없어서 1단계에서 접는다.

## 방법

- `solvers/lns/elf_lns.cpp`를 `solvers/regfit/elf_regfit.cpp`로 복사해 계측했다. 개선 이동(명령 수가 줄어드는 이동)이 레지스터 배치에서 실패하면 `RF 종류 red 절감 over 넘침 span 구간` 한 줄을 stderr에 찍는다. 이동 후 값 집합의 해시로 같은 이동을 한 번만 센다. 넘침은 수리(`repairOrder`) 뒤 가장 나은 순서의 최대 동시 사용 − 48, 구간은 그 순서에서 48을 넘는 시점의 수다.
- 엔진 구조: 후보 생성 단계에는 레지스터 제한이 없다. 배치 검사(`place`)에서 버린다. 예외는 `aware`(재료를 레지스터 여유가 있는 값으로 제한)인데 기본값 0이고, `run_cpp.py`는 0.5로 준다. 측정은 `aware=0`으로 해서 제한 없는 후보를 센다.
- 대상: 목표값 중앙값 48비트 이상 퍼즐 236개(48~55비트 128, 56비트 이상 108) 중 48~55비트 20개와 56비트 이상 20개. 목록은 `solvers/regfit/puzzles40.txt`. 출발은 `best/best.csv`, 퍼즐당 30초, 씨 1, 설정 `peq=0.5 pelim=0.05 pruin=0.8 ruink=12 aware=0 repair=2000 beamw=32`. 5개 동시. 로그 `solvers/regfit/run_m1.log`, 원자료 `m1.json`.

## 결과

| 항목 | 값 |
|---|---|
| 퍼즐 수 | 40 |
| 버려진 개선 이동 (중복 제외) | 9건 (퍼즐당 0.23). 퍼즐 2개(scored_0058 5건, scored_0183 4건)에만 있고 나머지 38개는 0건 |
| 절감 크기 1 / 2 / 3 이상 | 9 / 0 / 0 |
| 넘침 1 / 2 / 3 이상 | 2 / 2 / 5 (3이 3건, 4가 2건) |
| 넘친 구간 길이 | 4, 5, 11 (scored_0183) 와 24, 37, 37, 41, 64 (scored_0058) |
| 같은 30초에 실제로 줄어든 명령 | 40개 퍼즐 합 1 |

앞서 한 번 중단한 같은 설정의 실행에서도 15개 퍼즐 중 scored_0905에서 2건이 나왔을 뿐이다.

## 판단

- 판단 기준(퍼즐당 한두 건에 못 미치면 접는다)에 해당한다. 퍼즐당 0.23건이고 전부 절감 1이다. 절감 1짜리는 값을 다시 계산하는 수리로는 이득이 없고, 순서 옮기기만 가능한데 넘침 3 이상에 구간 24~64가 5건이라 이것도 어렵다.
- 이유: 이 퍼즐들은 이미 lns 여러 패스를 거쳐 개선 이동 자체가 드물다(30초에 40개 합 1개 감소). 레지스터는 병목이 아니라 "개선 이동이 없다"가 병목이다. 98%가 46개 이상에 닿는다는 사실과 별개로, 후보가 한도를 넘는 일이 드물다.
- 2단계(수리 구현, 대조군 비교, results/regfit.csv)는 하지 않았다.

## 한계

- 씨 1개, 30초. 개선 이동이 이렇게 드물면 표본이 작다. 그래도 40개 퍼즐에서 한 건도 2 이상 절감이 없었다.
- 수리 뒤 최선의 순서만 보고 넘침을 쟀다. 엔진의 수리가 더 잘하는 순서가 있을 수 있다.
