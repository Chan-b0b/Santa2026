## 2. 핵심 아이디어

1. **풀(pool)**: 레지스터에 지금 들어 있는 값 전부(최대 46~47개). 시작값, 작은 자릿수(1..k), 이전 체인의 중간값, 이전 목표값이 섞여 있다. 따로 "테이블 만들기 단계"를 크게 두지 않고, 앞 목표값 체인에서 나온 중간값이 그대로 다음 목표값의 테이블이 된다.
2. **S1**: 풀 값 둘의 연산 한 번으로 나오는 값 전부(약 2,000~2,500개). 사전 `값 -> (op, a, b)`. 명령 1개짜리 가상 테이블이다.
3. **일반화된 Horner 한 단계**: `v = c*m + d` 또는 `v = c*m - d`. 고정 진법이 아니라 **m 과 d 를 둘 다 풀에서 고른다.** m 마다 `v mod m` 과 같은 나머지를 가진 풀 값 d 가 있으면 명령 2개로 `log2(m)` 비트를 줄인다. 풀에 11~12비트 값이 40개쯤 있으면 m 이 2^10~2^12 인 적중이 상태마다 1~2개 나온다. 풀이 1..46 자릿수 테이블뿐이면 같은 탐색으로도 49비트 목표값에 11.7개가 들고, 임의의 11~13비트 값 46개면 7.8~8.0개다(합성 실험, 3절).
4. **역방향 beam**: 목표값 t 에서 시작해 위 단계를 거꾸로 적용하며 값을 줄이고, 풀 값(0개), S1 값(1개)에 닿으면 끝. 비용(명령 수)별 층으로 나눠 각 층에서 작은 값 W 개만 확장한다.
5. **가장 싼 것부터**: 매번 남은 목표값 전부에 beam 을 돌려 `비용 - 0.16*비트수` 가 가장 작은 목표값을 만든다. 하나 만들 때마다 풀이 바뀌므로 전부 다시 잰다.
6. **수명 기반 가상 풀 (vchain)**: 레지스터는 "앞으로 다시 쓰일 값"에만 필요하다. 명령을 SSA 로 기록하고 값마다 정의~마지막 사용 구간만 레지스터를 차지한다고 보면, 탐색이 고를 수 있는 풀이 48개가 아니라 지금까지 만든 값 거의 전부(100~160개)가 된다. 잎 하나의 정보량이 log2(46) 에서 log2(100+) 로 늘어난다. 이 생각은 relate 노트의 "SSA + 사후 레지스터 배정"에서 가져왔고, 여기서는 구간별 생존 값 수를 증분으로 추적해 재시도 없이 정확히 판정한다 (2.6절).

### 2.6 vchain: 수명 기반 가상 풀 (`solvers/chain/vchain.py`)

- `ssa`: 명령 목록 `(op, 피연산자 id, 피연산자 id, 값)`. `lu[id]`: 그 값의 마지막 사용 명령 번호.
- `cnt[T]`: T 번째 명령을 실행할 때 살아 있어야 하는 값의 수(정의 < T <= 마지막 사용). **모든 T 에서 cnt[T] <= 47 이면 레지스터 48개로 배정된다** (피연산자 최대 47개 + 결과 1개. 그 명령에서 죽는 피연산자의 레지스터는 결과가 물려받는다).
- 값 x 를 지금(T) 다시 쓰면 `(lu[x], T]` 구간의 cnt 가 1씩 늘고 `lu[x] = T` 가 된다. 자주 쓰는 값은 짧은 구간만 더하고, 오래 묵은 값을 되살리면 긴 구간에 1이 더해진다.
- **되살릴 수 있는 값**: `max(cnt[lu[x]+1 .. 지금]) <= vsoft(45)` 인 값. `rebuild` 때 뒤에서부터의 최댓값 배열 하나로 전부 판정한다. 이 값들 중 점수 상위 `vcap`(160~200)개가 탐색 풀이다. 퇴출이 없으므로 예전 목표값과 작은 값이 계속 남는다.
- 체인 하나를 내보낸 뒤 cnt 가 47 을 넘으면 되돌리고(`checkpoint`/`rollback`), 넘친 구간을 지나가는 되살린 값 중 가장 오래된 것을 금지한 뒤 그 목표값만 다시 탐색한다. 12번 안에 안 되면 이 설정은 실패로 처리한다(연습 퍼즐 200개에서 실패 0).
- `finalize`: 목표값에 기여하지 않는 명령을 지우고, 마지막 사용 시점에 레지스터를 풀어 주며 순서대로 배정한다.
- 관찰(practice_0008, 49비트 목표값 29개, 총 230개 명령): 알려진 값이 21개에서 235개로 자라는 동안 체인 길이가 12, 10, 9, 9, 8 … 에서 7 로 내려간다. 8192 미만의 작은 값은 13개에서 36개로만 늘고, 나머지는 큰 중간값이다. 큰 값도 맨 위 상태의 가수 d 로 3~4번씩 다시 쓰인다. cnt 최댓값은 178번째 명령쯤에 46~47 에 닿고, 그 뒤 마지막 목표값 3개는 다시 8개가 든다(레지스터 여유가 끝에서 모자란다).
- 합성 실험에서는 작은 값만으로 된 고정 풀 크기 46 / 64 / 80 / 100 / 140 에서 49비트 목표값이 7.9 / 7.55 / 7.18 / 6.95 / 6.68 개, 60비트가 9.73 / 9.18 / 8.98 / 8.7 / 8.0 개였다. 실제 풀은 작은 값이 적어 그만큼은 못 내려간다.
- `tie_s1=1`: 같은 비용의 체인이 여럿이면 S1 로 작은 값을 더 많이 새로 만드는 쪽을 고른다(그 값이 풀에 계속 남으므로). 연습 4개씩: shared 135.5 → 130.0, mixed 220.8 → 218.8, independent 231.2 → 232.0.
- `hot=30`: 나머지가 같은 가수 d 후보가 여럿이면 최근 30개 명령 안에 쓰인 값을 우선한다(되살리는 구간이 짧아 레지스터를 덜 묶는다). independent 232.8 → 230.8, shared 136.5 → 135.0, mixed 변화 없음.
- 풀이 커지면 탐색이 느려지므로 beam 폭을 16 으로 줄였다(폭 32 는 mixed 에서 2% 낫고 나머지는 같음. 폭 8 은 independent·shared 에서 1% 나쁨). `vsoft` 42~46, `vcap` 140~200 은 차이가 1% 안쪽이다.

## 3. 왜 이 정도가 한계인가 (무작위 목표값)

- 식 트리에서 명령 k 개는 잎 k+1 개다. 잎은 풀 값 하나를 고르는 것이라 잎당 정보가 log2(46) = 5.5비트를 못 넘는다. 연산자와 모양까지 쳐도 명령당 6비트 남짓이다.
- 합성 실험(임의 값 46개짜리 고정 풀, 무작위 목표값 30~40개): 40비트 6.6개, 49비트 7.8~8.0개, 60비트 9.7~10.5개. beam 폭을 32에서 1,000으로, S1 곱수 깊이를 6으로, F2 표를 켜도 값이 그대로였다(6.63→6.60, 7.87→7.83). 선형 체인 탐색은 포화 상태다.
- 풀 값의 크기 분포(10~14비트 균일, 6~13비트 로그균일 등)를 바꿔도 49비트 기준 7.8~8.8 범위였다. 16비트 값만 있는 풀은 실패가 생긴다.
- 따라서 풀 크기가 고정이면 independent 유형(무작위 목표값)에서 탐색을 더 세게 해도 줄지 않는다. 줄이는 방법은 (a) 풀을 키우는 것(2.6절: 풀 140개면 49비트가 6.68개), (b) "어떤 목표값을 언제 만드느냐"(선택 압력), (c) 구조가 있는 유형의 관계 이용이다.

## 4. 알고리즘 상세 (`solvers/chain/chain.py`)

### 4.1 Machine: 레지스터와 풀
- `loc`: 값 -> 레지스터. `emit(op, x, y, protect)` 는 값으로 명령을 내고, 결과가 이미 풀에 있으면 명령을 내지 않는다.
- 빈 레지스터가 없으면 점수가 가장 낮은 풀 값을 덮어쓴다. 현재 체인에서 뒤에 쓰일 값(`protect`)은 제외한다.
- 퇴출 점수(높을수록 남김): 고정(자릿수 테이블) > 관계 있는 값(4.5) > `-비트수`(작은 값 우선, pol=0). 사용 횟수나 최근성 가산(pol=1~3), 특정 크기 선호(pol=4~6)는 차이가 없었다.
- 체인이 끝나면 `reserve`(1~2)개가 비도록 줄인다(`trim`).
- vchain(`vcap` 설정)에서는 이 퇴출이 없다. 값은 버리지 않고 2.6절의 생존 구간 계산으로 쓸 수 있는지만 판정한다. 점수는 알려진 값이 `vcap` 을 넘을 때 탐색 풀을 고르는 데만 쓴다.

### 4.2 rebuild: 풀이 바뀔 때마다 표를 다시 만든다 (약 1.5ms)
- `S1`: 모든 쌍의 `+ - * /`.
- `resid[m]`: 풀 값 m 마다 `{d mod m: d}` (같은 나머지는 가장 작은 d).
- `allsorted`: 풀 값과 S1 값을 합쳐 정렬한 목록(근처값 검사용, `bisect`).
- `F2`(선택): S1 값과 풀 값의 연산 한 번(약 20만 개, 30ms). 명령 2개짜리 끝점.

### 4.3 find_chain(t): 역방향 이동 목록
상태 v 에서 다음 상태 c 로 가는 이동과 명령 수:

| 이름 | 정방향 식 | 명령 수 | 조건 |
|---|---|---|---|
| M | v = c*m | 1 | m 은 풀 값, m 이 v 를 나눔 |
| MA / MS | v = c*m ± d | 2 | d 는 풀 값, `resid[m]` 로 찾음 |
| MA / MS (S1) | v = c*m ± d | 3 | d = v mod m 또는 m - v mod m 이 S1 값 |
| M1, MA1, MS1 | 위와 같되 m 이 S1 값 | +1 | 얕은 깊이(`s1m`=2)에서만. S1 값 중 8192 이하 전부 시도 |
| N3 | v = m*q ± c | 2 (q 가 S1 이면 3) | 몫 q 가 풀/S1 값이고 나머지 c 가 작을 때. 나머지가 다음 상태 |
| N2 | v = s*m ± c | 3 | s 는 v/m 에 가장 가까운 S1 값 |
| 근처값 | v = x ± c | 1 (x 가 S1 이면 2) | 자식이 생길 때마다 가장 가까운 풀/S1 값 x 를 `bisect` 로 찾아, 차이가 v 의 1/8 미만이면 그 차이를 상태로 추가 |
| A, S, RS, D, RD | v = c±p, p-c, c/p, p/c | 1 | c 가 S1(또는 F2) 값일 때만 (끝내기용) |

- 끝점: c 가 풀 값이면 0, S1 값이면 1, F2 값이면 2.
- 근처값 검사를 "확장할 때"가 아니라 "자식이 생길 때" 하는 것이 중요하다. beam 은 작은 값만 확장하므로, 이전 목표값 근처에 떨어진 큰 자식은 확장되지 않아 관계를 놓친다.
- 탐색은 `g + 1 < 지금까지 최선` 인 동안만 층을 확장한다. `ub` 인자로 "이 비용 미만만 찾기"를 걸 수 있다(4.4에서 가지치기에 씀).
- 복원: 끝점에서 부모 포인터를 따라 올라가며 `(op, x, y)` 값 단계 목록을 만든다.

### 4.4 목표값 순서: 가장 싼 것부터 (`solve_cheapest`)
- 매 회 남은 목표값 전부에 `find_chain` 을 돌린다. 기준은 `비용 - alpha*비트수`(alpha=0.16). 이미 찾은 최선보다 나을 수 없는 탐색은 `ub` 로 일찍 끊긴다.
- 하나 만들면 풀이 바뀌므로 전부 다시 잰다. "같은 비용인 것들을 이어서 만들기"로 2~3배 빠르게 해 봤더니 independent 가 3.6% 나빠졌다(6개 퍼즐 평균 260.0 → 269.5). 매번 다시 재는 것이 값을 한다.

### 4.5 구조를 쓰는 장치
- **gcd 씨앗(`seed`=4)**: 목표값 쌍의 gcd 가 128 이상이면 후보. `(나누는 목표값 수 - 1) * 비트수` 순으로 4개까지 먼저 만든다. 이후 M 이동이 명령 1개로 그 비트만큼 줄여 준다.
- **관계 있는 값 보호(`relkeep`=2)**: 128 이상인 풀 값 x 가 (a) 남은 목표값을 나누거나 (b) 남은 목표값이 x 의 4096배 이하 배수에서 x/2^12 이내이거나 (c) x 가 남은 목표값 바로 위에 있으면 퇴출에서 보호한다. **목표값을 만든 직후, trim 전에 갱신해야 한다.** 처음에는 회차 시작 때만 갱신해서 방금 만든 목표값이 바로 퇴출됐고 효과가 0이었다. 고친 뒤 shared 8개 평균 146.1 → 140.6.
- **작은 퍼즐(`solve_tiny`)**: `value_limit` 24 이하는 "만든 값 집합(비트마스크)"을 상태로 한 너비 우선 탐색으로 최적해를 낸다. 해당 16개 퍼즐 합계가 63 → 57.

## 5. 유형별로 통한 것과 안 통한 것

수치는 연습 퍼즐 일부(family 당 4~12개)의 평균 길이 변화다.

**통한 것**
- 풀 값을 곱수와 가수로 같이 쓰는 역방향 탐색: 샘플 대비 1/8 수준. 모든 유형의 기반.
- 가장 싼 것부터 만들기: independent 266.0 → 255.4, shared 160.8 → 151.1, mixed 232.2 → 227.3, multiplicative 138.7 → 133.0.
- 근처값 이동(N1~N3): shared 159.1 → 154.7, multiplicative 137.3 → 134.9. independent 는 변화 없음.
- S1 곱수(깊이 2): independent 259.9 → 253.5, shared 157.2 → 154.6, multiplicative 135.9 → 133.1.
- 크기 보정 선택(alpha 0.16): multiplicative 130.0 → 125.5, mixed 224.8 → 221.3. 크기가 고르지 않은 유형에서 효과. 0.4 는 나빠진다.
- gcd 씨앗 4개: independent 242.7 → 238.2, shared 143.7 → 141.0, multiplicative 130.3 → 128.4.
- 관계 있는 값 보호: shared 146.1 → 140.6. practice_0004 는 131~134 → 119.
- 퍼즐별 여러 설정 중 최선: 설정 5개로 0.2~1.2% 정도. 설정 간 차이가 작다.

**안 통한 것**
- beam 폭 늘리기(32 → 128 → 512): 변화 없음.
- 큰 자릿수 테이블(1..16): 2~4% 나빠짐. 1..2~8 은 서로 비슷하다.
- 풀 값 크기를 특정 비트 수에 맞추는 퇴출 정책: 변화 없음. 풀 구성은 체인이 내놓는 값이 결정한다.
- F2 끝점(명령 2개짜리 표): 0.7~1.9% 줄지만 풀이 바뀔 때마다 30ms 가 든다. 보조 설정에서만 켠다.
- 곱 분해 `t = A*B ± d` (A, B 가 F2 값): 40비트에서 체인과 비슷(6~7개), 49비트 이상은 거의 안 맞는다.
- 같은 비용끼리 묶어 만들기: 3.6% 나빠짐.
- 숨은 기준값을 먼저 만들기(`hubseed`): `t/c`(c <= 64) 가운데 다른 목표값 3개 이상이 그 배수 근처에 있는 값을 먼저 만들었더니 shared 135.3 → 138.2, mixed 216.2 → 218.6 으로 나빠졌다. 기준값 근처의 목표값 하나를 일반 체인으로 만들면 그 값이 기준값 노릇을 하므로 따로 만드는 비용만 든다.
- 쓰이지 않는 명령 제거: 전체에서 17개.
- 작은 값 미리 만들기(`preseed`, vchain): 지금 풀의 S1 값 중 512~4095 범위에서 하나씩 골라 명령 1개씩으로 K 개를 먼저 만든다. K = 0 / 6 / 10 / 16 일 때 practice_0018 은 307 / 304 / 302 / 300 으로 줄었지만 practice_0034 는 275 / 275 / 278 / 279, practice_0008 은 224 / 228 / 231 / 223, practice_0003 은 252 / 250 / 253 / 254 로 일관된 이득이 없다. 참고로 임의의 12비트 값을 공짜로 K 개 주면(시작값에 덧붙이는 가상 실험) practice_0018 은 K = 8 / 16 / 32 에서 288 / 278 / 271, practice_0008 은 215 / 212 / 201 이 된다. 작은 값의 가치는 초반에 값 하나당 명령 1~2개쯤이라, 명령 1개를 주고 만들면 본전이다.
- 보호 기준을 느슨하게(x/2^5 이내): shared 141.9, mixed 220.1 로 조금 나빠짐.

**유형별 진단**
- independent: 목표값이 시작값과 무관한 균일 난수로 보인다(시작값의 곱에 대한 나머지, 진법 전개에서 구조를 못 찾음). 3절의 한계에 가깝다.
- shared: "기준값의 작은 배수 ± 작은 차이"가 층층이 쌓인 구조다(예: practice_0004 의 118043757 = 2×59021881 − 5, 11588835232 = 44×263382624 − 224). 이전 목표값이 풀에 남아 있기만 하면 N3, MA/MS, 근처값 이동이 명령 2~4개로 찾는다. 기준값 자체(4~7개)와 차이값(1~2개)이 남은 비용이다.
- multiplicative: 목표값이 "작은 인수 여러 개 × 큰 소인수" 꼴이 많다. 목표값끼리 정확히 공유하는 큰 인수는 적다(gcd 128 이상인 쌍이 퍼즐당 14개, 목표값 10개쯤). 작은 소인수를 하나씩 곱하는 것은 일반 체인보다 느리므로, 풀/S1 값으로 나누어떨어질 때만 쓴다.
- mixed: 위 세 가지가 섞여 있어 장치들이 부분적으로만 듣는다.

## 6. 다음에 해 볼 것

1. **vchain 의 작은 값 늘리기와 초반 비용**: 곱수로 듣는 것은 13비트 이하의 작은 값인데 체인 하나가 1개쯤만 남긴다(practice_0008 에서 29개 체인 동안 13 → 36개). 초반 5개 목표값이 12, 10, 9, 9, 8개로 뒤쪽(7개)보다 퍼즐당 13개쯤 더 든다. 작은 값을 명령 1개씩 주고 미리 만드는 것은 본전이었다(5절의 `preseed`). 명령 하나로 작은 값이 둘 이상 생기거나, 체인의 부산물로 작은 값이 더 나오게 하는 이동을 찾아야 한다.
2. **vchain 의 레지스터 예산 배분**: 지금은 되살릴 수 있으면 그냥 쓴다. 오래 묵은 값을 되살리는 비용(긴 구간)을 탐색 비용에 반영하면 끝 무렵의 부족을 줄일 수 있다.
3. **숨은 기준값 찾기**: shared 에서 목표값 여러 개가 `c*H + e` 로 걸리는 H 가 목표값이 아닌 경우(예: practice_0004 의 10050190, 10974276). 지금은 다른 목표값 체인이 우연히 지나가야 풀에 들어온다. H 를 그냥 먼저 만드는 것은 손해였다(5절). H 를 싸게 만드는 식(시작값의 짧은 식 둘의 곱, relate 노트 2절)까지 같이 찾아야 이득이 난다. 차이 e 가 수백~수천이라 작은 오프셋 gcd 로는 안 잡힌다. 목표값 쌍의 비 `t_j/t_i` 가 정수에 가까운 경우는 이미 쓰고 있고, 분모가 2 이상인 유리수 비는 independent 와 같은 빈도(우연 수준)였다.
4. **선택 압력 더 주기**: 상위 후보 2~3개를 실제로 만들어 보고 남은 목표값 비용 합이 가장 줄어드는 쪽을 고르는 1단계 내다보기. 3배 느려지므로 작은 퍼즐부터.
5. **같은 비용의 체인 중 고르기**: S1 로 새로 만드는 값이 다른 목표값의 체인에도 쓰이는 쪽을 우선.
6. **선형 체인이 아닌 모양**: 두 부분식이 모두 명령 3개 이상인 곱. 순수 Python 으로는 표 크기(F3 약 2^24)가 걸린다.

### 8.3 반영한 것

1. **숨은 밑 해독 (`decode.py` + `basescan.cpp`)** — quirk 에게서 배움.
   - `basescan`: d 를 2^11~2^23 전부 훑어 `r = |t mod± d| <= min(d/64, 8192)` 인 목표값을 적중으로 본다. quirk 의 기준(d/512, 최대 1024)보다 넓게 받는 대신 **가능도 점수**로 거른다: `E = sum log2(d/(2r+1))`, `점수 = E - log2 C(묶음 수, 적중 묶음 수) - log2((E ln2)^(k-1)/(k-1)!)`. 퍼즐 하나에 0.5초.
   - **묶음**: 서로 작은 유리수 배(q <= 64, 오차 (p+q)*2^13 이하)인 목표값은 같은 허브에서 나온 것이라 한 묶음으로 보고 묶음마다 가장 큰 증거만 센다. 이걸 안 하면 허브 하나가 우연히 d 의 배수 근처일 때 그 묶음 전체가 적중해 가짜 후보가 진짜 밑보다 높게 나온다(scored_0136 에서 가짜 5389510 이 95.8, 진짜 279761 이 84.6).
   - **쌍 검증**(quirk 방식): 같은 (t, r) 에 적중한 후보 d, d' 가 `d*d' | t - r` 이면 그 목표를 검증된 것으로 센다. 점수 14 이상인 후보끼리만 하고 검증 목표 3개 이상(또는 점수 27 이상)이면 받는다. 문턱을 6으로 내리면 난수형 퍼즐에서도 검증 3~4개짜리 가짜가 나온다(서로소인 두 후보가 같은 (t, r) 에 적중하면 자동으로 성립하기 때문).
   - 고를 때: 이미 고른 값과 공약수가 큰 후보(같은 밑의 배수/약수 변형)는 건너뛰고, 고른 밑과의 곱으로 **새로 설명되는 목표가 2개 이상**일 때만 추가한다(밑의 약수 조합으로 생긴 후보 제거). d/j 가 더 많이 적중하면 d/j 를 쓴다(2a 대신 a).
   - **2단계**: 고른 밑이 있으면 문턱을 6으로 낮춰 다시 훑고, 고른 밑과 짝을 이뤄 새 목표 3개 이상을 설명하는 후보를 더한다. scored_0361 의 614147(점수 6.6)이 이렇게 들어온다.
   - 결과: 1,000개 중 344개 퍼즐에서 밑이 나왔다(229초, `seeds.json`). 같은 시점 quirk 는 203개였다.
2. **밑을 먼저 만들기 (`Params.bases`, `Machine.seed_given`)**: 해독한 밑을 작은 것부터 `find_chain` 으로 만들고 시작한다. scored_0136 163 → 129, scored_0006 172 → 131, scored_0162 211 → 165 (설정 하나 기준).
3. **설명 보조값 (`decode.explain`, `Params.aux`, `Machine.seed_aux`)**: 밑이 정해지면 목표값마다 `t = k2*(k1*a*b + e) + r` 로 풀어 필요한 작은 값(k1, k2, |e|, |r|, 2^14 이하)을 모은다. 이 값들을 보조 목표로 삼아 명령 1개(또는 2개)에 되는 것부터, 하나 만들 때마다 다시 재며 만든다. 밑보다 먼저 한 번(`aux_pre=1`), 밑 뒤에 한 번 돈다. 먼저 만들면 밑 자체가 `작은 값*작은 값 ± 작은 값` 으로 싸게 나온다. scored_0136 126 → 111~113.
4. **자기 결과에서 거두기 (`run2.py` 의 `harvest`)** — lns 에게서 배움("끝난 프로그램의 값 전부를 재료로 다시 만들면 짧아진다"). 지금까지의 최단 프로그램에서 **두 번 이상 피연산자로 쓰인 2^14 이하의 값**을 거둬 보조 목표로 넣고 처음부터 다시 푼다. 짧아지면 그 결과에서 다시 거둔다(최대 3번). scored_0361 152 → 144 → 143 → 142, scored_0136 126 → 117 → 113, 밑이 없는 scored_0184 도 161 → 156 → 154 → 153. 값 재합성을 따로 구현하지 않고, 공유되는 작은 값을 앞으로 당겨 놓는 것만으로 lns 가 하는 일의 일부를 구성 단계에서 한다.
5. **느슨한 해독 + what-if**: 엄격한 해독에서 밑이 안 나온 퍼즐 중 길이/하한이 5.6 이하인 336개에 문턱을 낮춘 해독(1단계 점수 6, 2단계 3, d 는 2^10 부터)을 돌려 153개에서 후보를 얻었다(`seeds_weak.json`). 틀린 후보가 섞이므로 넣고 풀어서 짧아질 때만 채택하고, 밑만 넣은 결과가 기존보다 6개 넘게 길면 밑을 버린다.

### 8.6 안 통한 것

- 거둔 보조값에서 무작위로 25%를 빼고 다시 풀기(6번): scored_0361 에서 142 → 143~153. 거둔 집합이 이미 국소적으로 좋다.
- 설정 변형(W=32, alpha 0.10/0.22, s1m=3, digits 0/2, vsoft 43, hot 0): 142 대 140~148 로 ±2 안쪽. `f2=1` 은 가상 풀 160개에서 한 번에 100초가 걸려 못 쓴다.
- 설명 보조값을 여러 번 나오는 것만 넣기(2회 이상): 퍼즐에 따라 갈린다(scored_0136 은 전부 넣은 쪽 111, scored_0184 는 2회 이상만 넣은 쪽 129). 그래서 둘 다 돌려 짧은 쪽을 쓴다.
- gcd 씨앗(`seed=4`)을 해독한 밑과 같이 쓰기: scored_0136 에서 126 → 129. 밑이 있을 때는 끈다(`seed=0`). 밑을 만드는 순서만 바꿔도 126 과 122 로 갈린다(작은 것부터 대 해독 순위 순). 순서는 아직 what-if 에 넣지 않았다.
- 느슨한 해독은 수확이 적다: 153개 퍼즐에 후보가 나왔지만 밑/설명 설정이 이긴 것은 16개뿐이다.

### 8.8 다음 아이디어

1. **작은 값 표를 통째로 최적화하기.** 밑과 설명이 정해지면 필요한 작은 값의 집합이 나온다. 지금은 가장 싼 것부터 하나씩 만든다. 이것을 "시작값에서 이 집합을 전부 만드는 가장 짧은 프로그램"(값이 2^14 이하인 작은 다중 목표 문제)으로 따로 풀면 scored_0136 기준 10개쯤 남은 차이가 여기서 나온다. 값이 작아 너비 우선이나 beam 으로 풀 만하다.
2. **설명을 직접 조립하기.** `explain` 이 낸 `(a, b, k1, k2, e, r)` 를 탐색에 맡기지 않고 그대로 명령으로 내보내고, 탐색 결과와 비교해 짧은 쪽을 쓴다. 같은 허브를 쓰는 목표값을 묶어 허브를 한 번만 만들게 한다. 겹친 꼴은 e, r 후보를 여러 개 두고 다른 목표값과 겹치는 값을 고른다.
3. **해독 범위 넓히기.** (a) 2^23 넘는 밑(scored_0162 의 11178054): 큰 목표값 퍼즐만 dmax 를 2^26 으로. (b) 2^11 미만의 밑: 묶음 대신 "같은 d 가 서로 다른 허브 3개 이상에서 같은 짝과 검증되는지"를 세는 방식. (c) 밑 대신 허브를 직접 찾기: 묶음 안 목표값들의 `t_i/k_i` 가 일치하는 H 를 구하고 H 근처 값을 인수분해해 여러 허브가 공유하는 인수를 찾는다.
4. **거두기를 난수형에도.** `harvest` 반복은 밑 없는 퍼즐에서도 듣는다(scored_0184 161 → 153). 난수형 약 310개는 한 번 푸는 데 5~10초라 이번에 못 돌렸다. `run2.py all 60 5 2` 로 한 번 돌려 볼 것(약 20분 예상, 15분 제한에 맞추려면 둘로 나눠서).
5. **find_chain 을 C++ 로.** 지금 what-if 한 번이 1~3초다. 수십 배 빨라지면 밑 부분집합, 보조값 넣고 빼기를 퍼즐당 수백 번 시도하는 국소 탐색이 된다. 이번에는 해독과 구조 쪽이 급해서 손대지 않았다.
6. **값이 작은 퍼즐 전용 처리.** 목표값이 2^30 이하인 퍼즐은 시작값에서 2~3번 연산으로 닿는 값 전체 표를 만들 수 있다. 그 표에서 목표값 여러 개가 공유하는 값을 고르는 방식(search 접근법의 영역)을 가져온다.
