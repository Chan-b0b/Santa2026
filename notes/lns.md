## 1. 표현

- 프로그램을 값 그래프로 바꾼다. 노드 하나 = 명령 하나 = 값 하나, 피연산자 두 개를 가리킨다. 레지스터 번호는 버린다.
- 목표값마다 그 값을 처음 만드는 노드를 "필수"로 표시하고, 필수 노드에서 닿지 않는 노드는 지운다.
- 점수는 살아 있는 노드 수다.
- 출력할 때는 노드를 위상 순서로 늘어놓고, 값의 마지막 사용 시점에 레지스터를 풀어 주며 차례로 배정한다. 48개로 배정되지 않는 그래프는 채택하지 않는다.

## 2. 탐색: 값 하나를 주어진 재료로 만드는 가장 짧은 식

재료(context)는 "지금 그래프에 살아 있고, 다시 만들려는 노드의 후손이 아닌 값 전부"다. 후손을 빼는 것은 순환을 막기 위해서다.

비용 한도를 1부터 올려 가며 깊이 우선으로 찾는다(`solve`).

| 비용 | 형태 |
|---|---|
| 1 | 재료 둘의 연산 한 번 (S1 표) |
| 2 | S1 값과 재료의 연산 한 번 |
| 3 | S1 값 둘의 연산 한 번 (정렬된 S1 목록으로 합·차는 두 포인터, 곱은 약수 검사) |
| 재귀 | `v = q*c ± d` (c, d 는 재료. 나머지 표로 찾음), `v = q*c` , `v = c*q ± r` (q 가 재료나 S1 값이고 r 이 작을 때), 가까운 재료나 재료 둘의 합·차와의 차이, S1 값을 곱수로 쓰는 변형 |
| 긴 사슬 | 식 길이가 5를 넘으면 깊이 우선 대신 역방향 beam(비용 층마다 값이 작은 상태 32개)으로 같은 형태를 찾는다. 60비트 퍼즐의 길이 8~9짜리 사슬을 옮기려면 필요하다 |

S1 표와 나머지 표는 그래프 전체에 대해 하나만 두고, 조회할 때 "죽은 노드나 금지된 노드를 쓰는 항목"을 건너뛴다. 채택된 이동 30번마다 전부 다시 만든다.

## 3. 이동

1. **노드 재유도.** 노드 x 하나를 고른다. x 만을 위해 존재하던 조상(전용 원뿔)을 떼어 내고 x 를 재료로 다시 만든다. 새 식이 원뿔보다 짧으면 채택, 길이가 같고 값이 다르면 확률 `peq`로 채택한다.
2. **중간값 제거.** 2~4곳에서 쓰이는 중간값 x 를 금지하고, x 를 쓰던 노드들을 x 없이 다시 만든다. 늘어난 명령 수가 x 와 그 전용 조상 수보다 적으면 채택한다.
3. **여러 노드 다시 만들기(ruin).** 노드 x 와 그 이웃(피연산자, 같은 피연산자를 쓰는 형제, x 를 쓰는 노드) 가운데 2~12개의 정의를 한꺼번에 지운다. 이때 쓸모없어진 노드도 함께 사라진다. 지운 노드를 값이 작은 것부터 하나씩 다시 만든다. 전체 노드 수가 줄면 채택, 같으면 확률 `peq`로 채택한다.

같은 값이 그래프에 이미 있으면 식을 새로 만들지 않고 그 노드로 합친다.

이동 1만 쓰면 금방 멈춘다. 앞선 접근법들의 프로그램은 중간값을 여러 목표값이 나눠 쓰고 있어서, 노드 하나만 바꿔서는 줄일 곳이 거의 없다. 이동 3이 그 얽힘을 함께 푼다.

## 4. 레지스터

- 새 그래프마다 "예전 실행 순서를 최대한 지키는 위상 정렬"로 순서를 만들고 배정을 검사한다.
- 실패하면 다시 만든 노드의 위치를 바꿔 본다(첫 사용 직전, 재료가 준비된 직후). 그래도 실패하고 개선 이동이면 순서를 무작위로 조금씩 바꿔 넘치는 양을 줄여 본다(`repairOrder`).
- 시작할 때와 채택 40번마다, 그래프는 그대로 두고 순서만 바꿔 "동시에 살아 있는 값의 합"을 줄인다(`optimizeOrder`). 4개 퍼즐에서 4~10% 줄었다.
- 무작위 목표값 위주의 퍼즐은 입력 프로그램이 이미 레지스터를 거의 다 쓰고 있어, 찾은 개선 이동의 상당수가 여기서 버려진다.

## 5. 실행

```bash
g++ -O2 -march=native -std=c++17 -o solvers/lns/elf_lns solvers/lns/elf_lns.cpp
.venv/bin/python -I -u solvers/lns/run_cpp.py --secs 20 --procs 14 --seed 301 > solvers/lns/run.log 2>&1                      # 현재 최선에서 출발
.venv/bin/python -I -u solvers/lns/run_cpp.py --src results/relate.csv --from-src --max-tries 2 --secs 20 --procs 14 --seed 302   # 다른 접근법의 결과에서 출발
.venv/bin/python -I core/verify.py results/lns.csv --partial && .venv/bin/python -I core/merge.py
# 퍼즐 몇 개만 시험 (결과 파일을 쓰지 않음)
PROCS=8 .venv/bin/python -I solvers/lns/one.py solvers/lns/elf_lns 20 scored_0027,scored_0063 seed=1 pruin=0.8 ruink=12
```

- `run_cpp.py`는 `results/lns.csv`에 퍼즐별로 더 짧을 때만 쓴다. 모든 출력은 `check_program`을 통과한 것만 받는다.
- 퍼즐당 시간은 `--secs`에 프로그램 길이/150을 곱한 값이다(0.15~1.5배). 이미 하한인 퍼즐은 건너뛴다.
- `--from-src`: `results/lns.csv` 에 더 짧은 것이 있어도 `--src` 의 프로그램에서 출발한다. `--max-tries N`: 같은 출발 프로그램을 N번 돌렸으면 건너뛴다(`solvers/lns/seen.json`).
- 여러 실행기가 동시에 돌아도 `results/lns.csv` 는 잠금·병합 저장(`store.py`)이라 서로 덮어쓰지 않는다.
- 설정(`--opts`, 기본값 `peq=0.5 pelim=0.05 pruin=0.8 ruink=12 aware=0.5 repair=2000 beamw=32`): `peq` 같은 비용 채택 확률, `pelim` 이동 2의 비율, `pruin` 이동 3의 비율, `ruink` 이동 3에서 지우는 노드 수 상한, `aware` 레지스터 여유가 있는 값만 재료로 쓰는 비율, `repair` 순서 수리 반복 수, `beamw` 긴 사슬 beam 폭, `cap` 탐색 한 번의 확장 상한, `maxb` 식 길이 상한.

## 6. 근거와 출처

- 공개 저장소 `github.com/Juan-Severiano/santa-2026`의 README와 `rust/README.md` 설명에 따르면, 공개 13만대 해법(goodpjw2008)이 "노드의 전용 원뿔을 지우고 후손을 뺀 나머지 값으로 다시 만드는" 탐색으로 만들어졌다. 이 설명을 읽고 같은 구조로 직접 구현했다. 그쪽 코드나 제출 파일은 쓰지 않았다.
- 탐색의 재귀 형태는 chain 접근법의 `find_chain`(일반화된 Horner 역방향 탐색)과 같은 생각이다.

## 7. 효과가 있던 것과 없던 것

있던 것(25개 퍼즐 또는 무작위형 19개 퍼즐 시험 기준):
- 여러 노드를 함께 다시 만들기(ruin): 20초에 0.26% → 2.1%. 대상은 "한 노드와 그 바로 이웃 2~12개", 다시 만드는 순서는 "값이 작은 것부터"가 가장 좋았다.
- 다른 접근법의 최신 결과에서 출발하기: 같은 출발점에서 씨만 바꾸는 것보다 훨씬 크다(패스당 −975, −552 대 −140, −105).
- 긴 사슬용 beam: 무작위형 퍼즐이 30초에 0.09% → 0.5~0.8%.
- 실행 순서 최적화와 수리: 레지스터 때문에 버려지던 개선 이동 일부를 살린다.

없던 것: 같은 비용 이동을 레지스터 압박이나 작은 값 선호로 가려 받기, 조금 나빠지는 이동 허용, 최선으로 돌아가 크게 허물기(kick), 새 중간값을 표에 바로 반영, 다른 프로그램의 유도식 가져오기, 허브 투표, chain 변형 설정으로 새로 구성, 초반 노드 완전 탐색, 퍼즐당 시간 늘리기. 수치는 [lns.status.md](lns.status.md)의 "해 봤지만 효과가 없던 것"에 있다.

## 8. 남은 여지에 대한 판단

- 재합성을 거친 프로그램은 거의 모든 노드가 여러 곳에서 쓰이는 명령 1개짜리다(전용 원뿔 1~3). 노드 하나나 이웃 몇 개를 바꿔서는 더 줄지 않는다.
- 비용의 큰 덩어리는 초반이다. 목표 20개 이상 퍼즐에서 처음 5개 목표값에 무작위형 66~68개, 구조형 41~44개가 들고, 6번째 이후는 목표당 무작위형 6.1~7.0개, 구조형 3.0~3.5개다(17:50 측정). 초반은 풀을 짓는 비용이라 재합성으로는 못 고친다.
- 공개 자료(`research_notes/`)에 따르면 같은 종류의 기법을 쌓은 한 팀의 독자 해법은 139,271 이고, 공개 최고 128,491 은 여러 팀 해법의 퍼즐별 최선을 합친 값이다. 더 줄이려면 계열이 다른 새 출발점이 필요하다.

## 9. 다른 접근법이 가져갈 수 있는 것

- 무작위 49비트 목표값은 "최종 프로그램의 값 전부"를 풀로 쓰면 평균 6.28개로 만들어진다(실제 프로그램 안에서는 7.1개). 탐색을 세게 해도 차이가 없고 풀의 크기가 전부다(`exp_f2.py`).
- 실행 순서만 바꿔도 레지스터 압박이 4~10% 줄어든다(`exp_sched.py`). 만든 뒤에 순서를 다시 잡으면 그만큼 풀을 더 쓸 수 있다.
- 목표값 하나하나는 시작값 기준으로 난수와 구별되지 않는다(`control.py`). 구조는 목표값 사이에만 있다.
